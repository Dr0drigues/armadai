# Gestion des packs : mise à jour, scaffolding, sources distantes

Date : 2026-11-03 · Statut : lot livré (18 tâches du plan `docs/superpowers/plans/2026-11-03-pack-management.md`, closes) ; cette spec a été mise à jour après coup pour que la revue et la validation jugent contre le comportement réellement décidé, pas contre le texte d'avant l'exécution · Suite de : étape 3 (packs natifs, `docs/superpowers/specs/2026-10-13-step3-guided-creation-starters-design.md`) · Cadre tenu par `framer` (`armadai-rules`), non dupliqué ici · Placé avant le lot « watch animé ».

## 1. Intention

`armadai init --pack` installe un pack une fois, mais rien ne sait le remettre à jour ensuite. Le 2026-11-02, mettre à jour un pack déjà installé dans un projet (après une évolution du pack dans sa source) a demandé une marche manuelle mesurée : `unlink`, déplacement du dossier `.armadai/` existant, `init --pack --force`, `link`, puis à la main — retirer une copie d'un fichier de skill que `link` avait sautée (« already exists », message resté sur stderr sans que personne ne le voie), retirer des fichiers orphelins d'une cible qu'aucun manifeste ne connaissait plus, remettre une retouche locale de `project.yaml` effacée par le remplacement, et reconstituer un état de suivi de flow reparti de zéro. Vérifié le 2026-11-03 : quand le `.armadai/` modifié est celui du projet lui-même (pas un pack externe), `link` seul suffit — le problème est spécifique à la mise à jour d'un pack *source*.

Dimitri a par ailleurs demandé (2026-11-02/03, mots exacts en tête de ce document) : un `armadai link update` pour simplifier un re-link ; une mise à jour automatique des packs depuis une source qui évolue (EC2, Drive, dépôt Git) ; un dépôt privé GitHub `armadai-packs` à plusieurs packs, sans savoir s'il faut des sous-modules ; des commandes de pack (scaffolding, etc.) ; variabiliser les chemins propres à une machine qu'un pack ou un projet installé porterait en dur. Il a explicitement reporté deux décisions au lot : la forme de ce paramétrage, et le fait de pousser `armadai-packs` seulement une fois un pack paramétré.

**Clarification de fond (2026-11-03), mot pour mot, à la question « tu penses à quoi ? » de `lead`** : « J'avais en tête dans la conf armadai globale, on pointe cette registry (mon repo git -- peut etre se dire que l'on ait un système similaire à d'autres registries, avec un fichier "d'index", des dossiers avec les contenus), ça les clone quelque part et peu importe le dossier projet, je peux dire que je link un de ces packs qui est défini dans la registry, et dans l'idée, si j'ai 9 projets avec 7 fois le même pack, il est référencé qu'à un seul endroit ». Et une exigence complémentaire, mot pour mot : « si dans mes 7 projets exemples, j'ai des éléments spécifiques, je peux le faire sans impacter le pack en cache ».

Ce que le code porte déjà, vérifié : une source distante (`~/.config/armadai/registries.yaml`) est clonée une fois dans un cache (`source_cache_dir`, sous `~/.config/armadai/registry/starters/`), et un fichier d'index facultatif (`armadai-starters.yaml`) peut restreindre ou nommer les packs d'une source.

**Décisions prises avec Dimitri (2026-11-03), mot pour mot :**
- Découpe du lot : « Un seul lot, tout » — les cinq capacités (pack update, sync forcé, scaffolding, variables de pack, signal de nouvelle version) restent dans ce lot ; le risque de périmètre (R1) reste écrit, mais le lot n'est pas coupé.
- Forme des variables (portée) : « project.yaml + fichiers » — la substitution s'applique à `project.yaml` (blocs `native` compris) et aux corps des agents, skills et commandes.
- Traçabilité de l'origine d'un pack installé : « Via le link-manifest (Recommandé) » — un champ optionnel nouveau, format `version: 1` préservé, même logique empreinte / suppression-si-inchangé que `link`/`unlink`.
- Source des valeurs de variables (Question A) : d'abord « Combinaison », puis « ça peut aussi être intéressant de pouvoir versionner certaines variables aussi », puis, sur une proposition à trois couches par priorité croissante (1. fichier versionné du projet, partagé par l'équipe → 2. fichier local non versionné, propre à la machine → 3. variable d'environnement ; absente des trois : avertissement et valeur vide), Dimitri a répondu « Oui, ces 3 couches ». Noms de fichiers (`.armadai/vars.yaml` et `.armadai/vars.local.yaml` proposés) à confirmer au plan.
- Variable non définie (Question B) : « Avertissement + vide ».
- Retouche locale de `project.yaml` lors d'un `pack update` (Question C) : « Remplacer si inchangé (Recommandé) ». Affinée ensuite par la Question H : `project.yaml` est en fait fusionné clé par clé, pas remplacé en bloc (voir H).
- Scaffolding, `pack new` (Question D) : « Les 3 solutions m'intéressent (2. défaut, 1. --empty, 3. --project ?) », puis « --from-project » pour le nom du drapeau de capture. Donc : assistant interactif par défaut (sans drapeau), `--empty` pour un squelette minimal, `--from-project` pour capturer le `.armadai/` courant en pack.
- Signal de nouvelle version (Question E) : les quatre surfaces, en un seul choix multiple — « Commande `pack status` (Recommandé), sortie de `pack sync`, `list`/`inspect`, sortie de `link` » — toujours sans appel réseau, par comparaison au cache déjà synchronisé.
- Distinction par cible (claude/opencode) de ces cinq capacités : « Indépendantes (Recommandé) », comme `init --pack` l'est déjà.
- Mode copie conservé à côté du mode référence (Question F) : « Coexistence (Recommandé) » — les deux modes existent, un projet choisit le sien à l'installation.
- Épinglage de version (Question G) : « Tag/commit (Recommandé) » — la référence enregistre un tag ou un commit, versionné avec le projet ; `pack update` avance explicitement cette épingle.
- Forme et portée de la surcouche locale (Question H) : « Remplacement par chemin (Recommandé) » — un fichier du projet au même chemin qu'un fichier du pack le remplace entièrement, un chemin absent du pack s'ajoute ; `project.yaml` seul fait exception et est fusionné clé par clé (pour garder des retouches comme `policy.free_agents` sans perdre les clés que le pack fournit).
- Où vit la référence (Question I) : « project.yaml versionné (Recommandé) ».
- Forme du fichier d'index de la registry (Question J) : « Nouvel index versionné (Recommandé) » — un index avec des métadonnées par pack (nom, chemin, version) ; `armadai-starters.yaml` reste lu pour compatibilité avec les sources qui n'ont que l'ancien format.
- Ce que `pack update` fait avec plusieurs projets référents (Question K) : « Lister les référents » — un registre des projets référents existe ; `pack update` liste ceux à relier, sans jamais les toucher lui-même.
- Où vit le registre des projets référents (Question L) : « Fichier dans `~/.config/armadai` (Recommandé) » — une entrée (pack, chemin de projet) ajoutée à l'installation en mode référence et à chaque `pack update` réussi ; un chemin devenu invalide (projet déplacé ou supprimé) est signalé, jamais retiré en silence.

**Décisions prises au cadre avec Dimitri (2026-11-03), mot pour mot (`framer` tient le fichier de cadre, non reproduit ici) :**
- Moment de la substitution des variables : « Au link seulement (Recommandé) » — `.armadai/` garde littéralement `{{var.name}}` ; seul `link` résout, et seulement dans les sorties compilées (`.claude/`, `opencode.json`).
- Syntaxe : « {{var.name}} + ARMADAI_VAR_ » — une variable de pack s'écrit `{{var.name}}` (jamais confondue avec `{{var}}` des templates d'agents, syntaxe distincte à dessein), la couche environnement se lit `ARMADAI_VAR_<NOM>`.
- Architecture : « Pur dans le modèle (Recommandé) » — la référence à un pack est une clé optionnelle nouvelle de `project.yaml` (`schema_version` reste `1`) ; la fusion (surcouche par chemin, `project.yaml` clé par clé) et la substitution de variables sont des fonctions pures d'`armadai-model` ; le binaire (`crates/armadai`) lit l'environnement, les fichiers de variables, le cache et le registre des référents, et les passe à ces fonctions.
- Épinglage (complète la Question G) : « 1. avec possibilité de placer un `latest` ou équivalent (idem, si on met `@1` ou `@^1.3`, ce devrait être exploitable) » — la référence déclare une plage (`@1.2.3` exact, `@latest`, ou une plage semver comme `@^1.3`) ; sur une machine neuve, le contenu de la version utilisée doit déjà être dans le cache (sinon `pack sync` est requis, jamais déclenché tout seul). Pour que la plage soit reproductible en équipe : « Fichier verrou versionné (Recommandé) » — la plage reste dans `project.yaml`, un fichier verrou séparé, versionné, enregistre la version et le commit résolus ; `link` lit toujours le verrou (jamais la plage), seul `pack update` l'avance. Résolution d'une plage semver : « Crate semver (Recommandé) » — la dépendance `semver` n'est ajoutée qu'à `crates/armadai` (jamais à `armadai-model`, qui reste pur : `cargo build -p armadai-model` le garantit déjà). Ce que la plage résout contre : « Les deux. si trop complexes, voir si en sub module c'est plus simple » — l'index (Question J) s'il liste des versions, sinon des tags git préfixés `<pack>-vX.Y.Z` ; une source archive n'a pas de tags, donc l'index y est obligatoire dès qu'une plage est utilisée ; un repli par sous-modules Git, si cette double résolution s'avère trop complexe à l'usage, reste à évaluer au plan (pas une décision prise ici).
- Traçage de l'origine en mode copie : « Section `packs:` du manifeste (Recommandé) » — le link-manifest gagne une section `packs:` qui enregistre, par pack installé en mode copie, son nom et sa version. Le link-manifest n'étant pas versionné (règle déjà en vigueur), un projet fraîchement cloné n'a pas cette section : `pack update` en mode copie y **refuse** explicitement (origine inconnue), plutôt que de deviner.
- Registre des projets référents : « Nouveau fichier (Recommandé) », indépendant d'un éventuel fichier existant de projets connus (`projects.json` ou équivalent) — propre à ce lot, pas une réutilisation.
- `armadai link --update` : « Hors lot (Recommandé) » — la demande initiale de Dimitri d'un `link update` pour « simplifier un re-link » n'est pas reprise dans ce lot ; `pack update` (objectif 1) couvre le besoin mesuré.
- Contenu du verrou (complète l'épinglage) : « Version + tag + commit (Recommandé) » — le verrou enregistre les trois ; le **commit fait foi** (un tag peut être déplacé) : `link` résout toujours contre le commit verrouillé, jamais contre le tag seul. Si le tag ne pointe plus sur ce commit (déplacé dans la source), `pack sync` le signale, sans rien changer au verrou de son propre chef. Pour une source archive (pas de commit git) : version + empreinte du contenu, la même logique s'appliquant à l'empreinte.

**Décisions prises pendant l'exécution (2026-11-03), une ligne par décision, citation puis ce qu'elle change** (source : registre d'avancement de `lead` et section 7 du plan) :
- Gate si la vue du pack ne s'ouvre pas : « Bloquer » — revient sur l'« approximation » prévue en conception (« pas d'avis »). Seule une erreur liée au pack (verrou ou instantané manquant) fait désormais refuser le gate ; un projet invalide pour une autre raison, sans rapport avec le pack, reste sans avis comme aujourd'hui.
- Le link-manifest (local, non versionné) peut porter une valeur de variable résolue : « Accepter et documenter » — ce n'est pas corrigé, seulement documenté (`starter-packs.md`, tâche 18) : un secret passé par `ARMADAI_VAR_*` peut donc apparaître dans ce fichier local.
- Une version demandée à `pack update` hors de la plage déclarée : refuser (texte proposé puis validé, voir critère 19), rien n'est changé.
- Un projet déjà invalide avant `pack add`/`pack update` : « Refuser sans blâmer » — un message distinct dit que le projet était déjà invalide, sans accuser la mise à jour ; `pack add` reçoit la même règle.
- Le message « would make the project invalid » (M13) ne sort que si c'est la mise à jour elle-même qui introduit l'erreur — jamais pour un projet déjà invalide avant (précise la décision précédente).
- Forme d'affichage d'une source de pack : « Secrets seulement » — après un premier essai qui masquait aussi une URL SSH à tort, seuls `user:pass@`, une requête et un utilisateur sur http/https sont masqués ; une URL SSH s'affiche telle quelle. Rapprochée du masquage déjà en vigueur pour `registries.yaml`.
- `link` qui échoue après que `pack add`/`pack update` ont écrit de nouveaux fichiers : « Remettre `.claude/` aussi » (deux modes) — tout est restauré, `.armadai/` et les sorties compilées ; affiné ensuite pour ne copier/supprimer que les chemins que `link` a réellement touchés (une première version copiait des arbres entiers, mesurée à 1,28 Go de RSS sur un worktree réel).
- Une fusion de `project.yaml` en mode copie qui change sa forme écrite (commentaires, mise en page) : « Avertir » — avertissement nommé, jamais silencieux.
- Les messages selon l'état de `.armadai/` : « M8/M9 selon `.armadai/` » — un message distinct pour « aucune trace d'un pack installé » (M9) et pour « trace illisible ou absente après un clone » (M8) ; « deux copies » (deux origines de copie à la fois) : refus plutôt que de deviner laquelle mettre à jour.
- Le registre des projets référents : une erreur sans écraser pour un format non supporté, et un verrou de fichier contre une perte d'entrée en écriture concurrente (mesurée dans 27 essais sur 160 avant la correction).
- `armadai skills` lit la vue effective d'un projet référençant un pack, comme `list`/`inspect` (« Lire la vue effective ») ; `inspect`/`skills show` affichent la couche d'origine d'un élément venant du pack.
- Un tag supprimé dans la source d'un pack référencé : « Avertir » (texte M3b, le verrou garde son commit) ; le cas où la source a aussi fait `git gc` (le commit verrouillé devient irrécupérable) reste un défaut connu, à ouvrir en issue séparée après le lot, pas corrigé ici.
- `pack new --empty`/`--from-project` : les dossiers vides du pack créé portent un `.gitkeep`, que l'installation de ce pack (`init --pack`) n'affiche jamais comme un fichier ignoré.
- `armadai pack --help` : une aide longue proposée puis validée par Dimitri avant d'être commitée (texte dans `cli/mod.rs`, non reproduit ici).

**Correction de fait (lead, mesurée sur un pack réel, 2026-11-03)** : une version antérieure de cette spec affirmait que `project.yaml` ne porte aucun chemin. C'est faux. Le bloc `native:` de `project.yaml` (`Manifest.native`, `crates/armadai-model/src/types.rs:98`, type `BTreeMap<String, NativeValue>` où `NativeValue` est un passe-plat JSON transparent, `types.rs:9-15`) est recopié tel quel — sans validation de son contenu — dans `.claude/settings.json` (`compile/claude_settings.rs`, qui ne découpe que les clés connues comme `permissions.allow`/`permissions.additionalDirectories` pour savoir ce qu'il possède) et dans `opencode.json` (`compile/opencode.rs:166-190`, fusion directe ; seuls une collision de clé ou un `.` dans une clé sont refusés). Un pack réel peut donc porter des chemins machine-spécifiques aussi bien dans `native.claude.permissions.*` / `native.opencode.permission.*` de `project.yaml` que dans le corps d'un agent, d'une commande ou d'une skill — mesuré sur un pack réel : 9 chemins dans `project.yaml` (blocs `native`), 7 dans des corps d'agents, d'une commande et d'une skill. La seule validation existante sur `native` (`armadai-model/src/check.rs:472-476`, `native_keys`) vérifie que la clé de premier niveau nomme une cible connue, jamais le contenu.

## 2. Objectifs, non-objectifs, anti-objectifs

**Objectifs** (un seul lot, décision du 2026-11-03) :
1. Deux modes d'installation d'un pack, coexistants (Question F), choisis par le projet à l'installation :
   - **copie** (comportement d'aujourd'hui, affiné) : les fichiers du pack sont recopiés dans `.armadai/` ; le link-manifest gagne une section `packs:` qui trace nom et version du pack installé ; `pack update` remplace un fichier inchangé depuis l'installation, garde et signale un fichier retouché, retire une cible abandonnée — et **refuse explicitement** s'il ne trouve pas cette section (projet fraîchement cloné : le manifeste n'est pas versionné, l'origine est inconnue).
   - **référence** (nouveau) : `project.yaml` (versionné) porte le nom du pack, sa source et une plage (un tag/version exact, `@latest`, ou une plage semver comme `@^1.3`, Question G) ; un fichier verrou séparé, versionné, enregistre la version et le commit résolus pour cette plage. `link` lit toujours le verrou (jamais la plage, jamais le réseau) pour choisir le contenu dans le cache déjà synchronisé, et le fusionne avec la surcouche du projet (remplacement par chemin, `project.yaml` fusionné clé par clé, Question H) — fusion et substitution en fonctions pures d'`armadai-model`. `pack update` avance le verrou et relie le projet, et liste (sans les toucher) les autres projets connus qui référencent le même pack (Question K).
   - Dans les deux modes : jamais de perte silencieuse d'une retouche locale, jamais de cible abandonnée laissée derrière.
2. Rafraîchir le cache local d'une source distante de packs (git ou archive) sans attendre qu'un nom de pack manque : aujourd'hui une source n'est synchronisée qu'au premier échec de résolution locale d'un pack, jamais ensuite (mesuré : aucune fonction ni commande de rafraîchissement forcé n'existe, `crates/armadai/src/starters_registry/mod.rs`). En mode référence, ce rafraîchissement est la première moitié de « mettre à jour » : rafraîchir une fois, profiter à tous les projets qui référencent la source.
3. Un paramétrage pour les valeurs propres à une machine, en syntaxe `{{var.name}}` (distincte de `{{var}}` des templates d'agents), substitué **au `link` seulement** — jamais à l'installation ni dans `.armadai/` lui-même — dans les sorties compilées issues de `project.yaml` (blocs `native` compris) et des corps des agents, skills et commandes d'un pack. Résolu par trois couches, par priorité croissante : fichier versionné du projet, puis fichier local non versionné, puis `ARMADAI_VAR_<NOM>` (environnement) — la dernière qui répond gagne, donc l'environnement l'emporte sur le fichier local, qui l'emporte sur le fichier versionné (Question A). Absente des trois : avertissement et valeur vide dans la sortie compilée (Question B), jamais une erreur silencieuse.
4. Des commandes de pack : `pack new` (assistant interactif par défaut, `--empty` pour un squelette minimal, `--from-project` pour capturer le `.armadai/` courant) et `pack update` au minimum ; nommage complet à trancher au plan (`update` seul est déjà pris par l'auto-mise-à-jour du binaire).
5. Un signal de nouvelle version de pack disponible, visible sur les quatre surfaces décidées (`pack status`, sortie de `pack sync`, `list`/`inspect`, sortie de `link`), toujours sans aucun appel réseau — la comparaison se fait contre le cache déjà synchronisé par ailleurs et le nouvel index versionné (Question J).

**Non-objectifs (ce lot)**
- Les sous-modules Git pour `armadai-packs` : inutiles pour un dépôt à plusieurs packs (fonctionne déjà tel quel, voir Conception) ; un repli par sous-modules pour la résolution de versions reste une option à évaluer au plan si l'index/tags s'avère trop complexe (pas une décision prise ici).
- Codex, Copilot (hors v1, cf. `project_v1_scope_2026-10-27`).
- Le contenu du pack `armadai-packs` lui-même : il reste privé, hors dépôt public, et n'est poussé qu'une fois un pack paramétré (mot de Dimitri).
- Une validation du contenu du bloc `native:` au-delà de ce qui existe déjà (clé de premier niveau connue) : ce lot substitue des variables dedans (au `link`), il ne valide pas les chemins qui en résultent.
- Une distinction de comportement par cible (claude/opencode) pour ces cinq capacités : elles restent indépendantes de la cible (décidé).
- Migrer automatiquement un projet déjà installé par copie vers le mode référence : un projet existant garde son mode jusqu'à un geste explicite (cohérent avec la coexistence décidée, Question F).
- Relier automatiquement, à distance, les autres projets référents listés par `pack update` : ils sont listés, jamais touchés (Question K).
- `armadai link --update` : décidé hors lot (« Hors lot (Recommandé) ») ; `pack update` couvre le besoin mesuré.

**Anti-objectifs**
- Écraser en silence un fichier de pack qu'un utilisateur a modifié à la main : toujours un avertissement nommé, jamais une perte non signalée.
- Perdre `.armadai/state/` ou le link-manifest d'un projet lors d'une mise à jour de pack.
- Toucher le réseau dans `link` (règle existante, non négociable) ni dans aucune des quatre surfaces du signal de version (objectif 5) ni dans la résolution d'une plage de version : la comparaison et la résolution se font toujours contre un cache et un verrou déjà présents, jamais en déclenchant une synchronisation.
- Résoudre une variable manquante par une valeur devinée ou une erreur fatale qui bloquerait toute la commande : le choix tranché est avertissement + valeur vide (Question B), pas un silence total ni un blocage.
- Qu'une surcouche propre à un projet modifie le pack en cache, ou se propage à un autre projet qui référence le même pack (exigence de Dimitri, mot pour mot en tête de ce document).
- Faire deviner à `pack update` l'origine d'un pack en mode copie quand elle est inconnue (projet fraîchement cloné) : il refuse, il ne devine jamais.
- Faire fuiter la résolution de plage semver (dépendance `semver`) dans `armadai-model` : la portabilité du modèle pur (déjà gardée par `cargo build -p armadai-model`) ne doit pas régresser.

## 3. Contraintes

- `init --pack --force` garde aujourd'hui tout fichier existant (un avertissement chacun) et l'ancien `project.yaml` gagne sur celui du pack : ce comportement reste celui d'une première installation en mode copie ; `pack update` est une commande distincte avec sa propre politique de conservation, pas une redéfinition de `--force`.
- Aucune information sur l'origine d'un pack installé n'est conservée aujourd'hui nulle part. En mode copie, une nouvelle section `packs:` du link-manifest comble ce manque (nom, version) ; en mode référence, `project.yaml` lui-même porte la source et la plage, et un fichier verrou versionné porte la version et le commit résolus.
- `.armadai/link-manifest.yaml` reste en `version: 1` (règle du dépôt) : tout ajout (la section `packs:` comprise) y est un champ optionnel, jamais un changement de version qui rendrait les manifestes existants illisibles ; un test lit un manifeste écrit par la version précédente. Le link-manifest n'étant pas versionné (règle déjà en vigueur : `.armadai/` est versionné sauf `link-manifest.yaml`, `.migrated/` et `state/`), un clone frais n'a pas la section `packs:` : c'est la cause directe du refus décidé pour `pack update` en mode copie après un clone.
- La référence à un pack (mode référence) est une clé optionnelle nouvelle de `Manifest` (`armadai-model`) ; `schema_version` reste `1`. La fusion (surcouche par chemin, `project.yaml` clé par clé) et la substitution de `{{var.name}}` sont des fonctions pures d'`armadai-model`, qui ne dépendent ni de l'environnement, ni du système de fichiers, ni du réseau : elles reçoivent déjà résolus (version/commit du verrou, valeurs de variables) ce qu'elles appliquent. `crates/armadai` (le binaire) lit l'environnement, les fichiers de variables, le cache et le registre des référents, résout la plage semver (dépendance `semver`, ajoutée seulement là), et appelle ces fonctions.
- Le bloc `native:` de `project.yaml` est un passe-plat JSON non structuré (`types.rs:9-15`) : la substitution de variables doit donc parcourir des valeurs JSON libres (chaînes, et récursivement les tableaux/objets qu'elles contiennent), pas un schéma connu à l'avance — proche de ce que `render_value` fait déjà pour les templates d'agents (parcours récursif des chaînes), et ne doit jamais convertir un type (un entier ou un booléen du JSON reste tel quel, seule une valeur `String` est candidate à la substitution). Elle n'a lieu qu'au `link`, jamais écrite dans `.armadai/` lui-même.
- La syntaxe `{{var.name}}` (variables de pack) est distincte de `{{var}}` (templates d'agents, `crates/armadai-core/src/template.rs`) : les deux mécanismes coexistent sans se confondre, et ne partagent pas nécessairement leur implémentation.
- Un fichier de variables versionné (`.armadai/vars.yaml`, nom à confirmer au plan) voyage avec le dépôt de l'équipe ; un fichier de variables local (`.armadai/vars.local.yaml`, nom à confirmer) est propre à la machine, non versionné — comme `link-manifest.yaml` et `state/`, à ajouter à `.armadai/.gitignore`. La couche environnement se lit `ARMADAI_VAR_<NOM>`.
- Une source distante git est clonée par `git clone --depth 1` (jamais `--recurse-submodules`) et mise à jour par `git pull --ff-only` seulement si déjà clonée ; une archive est téléchargée par `curl` (https, 300 s, 100 MiB) puis extraite et vérifiée avant de remplacer atomiquement le cache précédent. Le cache (`~/.config/armadai/registry/starters/<clé>`) est déjà l'endroit unique que Dimitri décrit (« il est référencé qu'à un seul endroit ») : le mode référence relie un projet à ce cache, il ne crée pas de second cache.
- Le nouvel index versionné (Question J) porte, par pack, au moins son nom, son chemin dans la source et une forme de version ; `armadai-starters.yaml` (aujourd'hui : juste `packs: [{path: ...}]`) reste lu pour les sources qui n'en ont pas encore un. Une résolution de plage semver se fait contre les versions que l'index liste s'il en liste, sinon contre des tags git préfixés `<pack>-vX.Y.Z` ; une source archive n'a pas de tags, l'index y est donc obligatoire dès qu'une plage est utilisée.
- `project.yaml` en mode référence porte la source du pack et sa plage (exact, `@latest`, ou semver) ; le fichier verrou (nom à confirmer au plan) porte la version et le commit résolus. Les deux sont versionnés avec le projet, donc lus et partagés par toute l'équipe qui le clone ; `link` ne lit jamais la plage directement, seulement le verrou.
- Barrière complète, mutation pour chaque test, revue indépendante avant fusion (règles du dépôt).

## 4. Conception

*(F-L et les décisions de cadre tranchées ; le repli par sous-modules pour la résolution de versions, s'il s'avère nécessaire, est à évaluer au plan.)*

- **Sources et cache** : inchangés dans ce lot sauf l'ajout d'un déclenchement explicite de synchronisation (objectif 2), probablement une commande qui appelle directement `starters_registry::sync_starters` sur les sources effectives (utilisateur ∪ projet), sans attendre un miss.
- **Dépôt `armadai-packs`** : un dépôt Git ordinaire, un pack par dossier à sa racine (ou listé par le nouvel index si d'autres fichiers y vivent aussi) ; aucune configuration de sous-module pour la structure multi-packs elle-même. Documentation à ajouter à `docs/wiki/starter-packs.md`.
- **Mode copie** : inchangé dans ses grandes lignes (c'est `init --pack` aujourd'hui), affiné par `pack update` (remplace si inchangé, garde+signale si retouché, retire une cible abandonnée, `project.yaml` fusionné clé par clé) et désormais tracé par une section `packs:` du link-manifest (nom, version). Sans cette section (projet fraîchement cloné, le manifeste n'étant pas versionné), `pack update` refuse explicitement plutôt que de deviner l'origine.
- **Mode référence** : `project.yaml` porte, versionnées, la source du pack et une plage (`@1.2.3`, `@latest`, ou `@^1.3`). Un fichier verrou séparé, versionné, enregistre la version, le tag et le commit résolus pour cette plage (ou, pour une source archive sans commit git, la version et une empreinte du contenu) ; `link` résout toujours contre le **commit** (ou l'empreinte) verrouillé, jamais contre le tag seul, qui peut avoir été déplacé dans la source — `link` ne lit que le verrou (jamais la plage, jamais le réseau) pour choisir le contenu du cache, puis fusionne (fonctions pures d'`armadai-model`) : un fichier du projet au même chemin qu'un fichier du pack le remplace entièrement, un chemin absent du pack s'ajoute en plus (surcouche par chemin) ; `project.yaml` lui-même est fusionné clé par clé (le pack fournit ce qu'il déclare, le projet garde ses propres clés — par exemple `policy.free_agents` — sans jamais perdre l'une ou l'autre). Le résultat est compilé vers `.claude/`/`opencode.json` comme aujourd'hui. « Mettre à jour » un projet en mode référence = avancer le verrou (au meilleur repère de la plage dans le cache rafraîchi, ou un repère donné) puis `link`.
- **Résolution de la plage (binaire, pas le modèle)** : `crates/armadai` résout une plage semver (dépendance `semver`, ajoutée seulement à ce crate) contre les versions listées par l'index de la source si elle en liste, sinon contre les tags git `<pack>-vX.Y.Z` ; une source archive exige l'index dès qu'une plage est utilisée. Le résultat (une version et un commit précis) est ce que le fichier verrou enregistre et ce que les fonctions pures d'`armadai-model` reçoivent — elles ne résolvent jamais de plage elles-mêmes.
- **La surcouche n'écrit jamais dans le cache (exigence, pas une question)** : le cache d'une source (`~/.config/armadai/registry/starters/<clé>`) n'est modifié que par une synchronisation (`pack sync`/`init`/`pack update` qui rafraîchit), jamais par la fusion que `link` fait pour un projet donné ; la fusion lit le cache et écrit uniquement dans les sorties compilées du projet. Deux projets référençant le même pack, l'un avec une surcouche et l'autre sans, lisent donc le même cache et ne s'influencent jamais l'un l'autre.
- **Variables (au `link` seulement, syntaxe `{{var.name}}`)** : `.armadai/` garde littéralement `{{var.name}}` dans `project.yaml` (parcours récursif des valeurs `String` de `native:`, plus les champs texte usuels) et dans les corps Markdown/YAML des agents, skills, commandes d'un pack — qu'il soit copié ou référencé. `link` seul résout, par trois couches par priorité croissante (fichier versionné du projet → fichier local non versionné → `ARMADAI_VAR_<NOM>`, la dernière qui répond gagne : l'environnement l'emporte sur le local, qui l'emporte sur le versionné), absente des trois : avertissement nommé et valeur vide dans la sortie compilée. La fonction de substitution elle-même est pure (`armadai-model`), reçoit déjà les valeurs résolues ; le binaire lit les trois couches et les lui passe.
- **Scaffolding (décidé)** : `pack new` sans drapeau est un assistant interactif (dans l'esprit de `new agent`/`new flow`) ; `pack new --empty` écrit un squelette minimal (`pack.yaml` `format: 1`, `project.yaml` par défaut, dossiers vides) ; `pack new --from-project` capture le `.armadai/` du projet courant en pack, automatisant la procédure manuelle déjà documentée dans « Creating Custom Packs » du wiki.
- **Signal de version (décidé pour les surfaces)** : une commande `pack status` dédiée (surface principale), plus trois reprises (sortie de `pack sync`, `list`/`inspect`, sortie de `link`), toutes lisant le même état (cache et nouvel index déjà synchronisés, comparés au verrou ou aux fichiers que le projet référence ou a installés), jamais de déclenchement réseau propre à l'une de ces quatre surfaces.
- **Registre des projets référents (décidé)** : un nouveau fichier sous `~/.config/armadai/` (nom à confirmer au plan), indépendant d'un éventuel fichier de projets connus déjà présent par ailleurs, une entrée par (pack, chemin de projet), écrite à chaque installation en mode référence et mise à jour à chaque `pack update` réussi. `pack update`/`pack status` le lisent pour lister les projets référents d'un pack sans jamais les toucher. Un chemin devenu invalide (projet déplacé ou supprimé) est signalé, jamais retiré en silence.

## 5. Critères d'acceptation

**Pack update (objectif 1)**
1. L'installation d'un pack choisit son mode (copie ou référence, Question F) ; en mode référence, `project.yaml` versionné porte le nom du pack, sa source et une plage (`@1.2.3`, `@latest` ou `@^1.3`, Question G), et un fichier verrou versionné distinct porte, pour cette plage, la version, le tag et le commit résolus (ou, pour une source archive, la version et une empreinte du contenu).
2. `link` résout toujours contre le commit (ou l'empreinte) du verrou, jamais contre le tag seul ni la plage ni le réseau, pour choisir le contenu d'un pack référencé dans le cache déjà synchronisé ; si ce commit (ou cette empreinte) n'est pas présent dans le cache local, `link` et `pack update` donnent une erreur nommée (pas un appel réseau, pas un plantage) qui dirige vers `pack sync`. Si le tag du verrou ne pointe plus sur ce commit dans la source (déplacé), `pack sync` le signale, sans modifier le verrou lui-même.
3. Deux machines qui partagent le même projet versionné (même verrou) et ont chacune synchronisé la source du pack compilent des sorties strictement identiques à partir du même contenu de cache — la plage ne fait jamais diverger deux membres d'une équipe qui n'ont rien changé eux-mêmes.
4. `pack update` en mode référence avance le verrou (au meilleur repère de la plage dans le cache rafraîchi, ou un repère donné) et relie (`link`) le projet courant contre ce contenu ; il liste aussi, depuis le registre des projets référents, les autres projets connus qui référencent le même pack (Question K), sans jamais les modifier lui-même.
5. En mode copie, `pack update` remplace un fichier du pack resté inchangé depuis l'installation et garde, en le signalant par son nom, tout fichier modifié à la main (jamais sauté en silence, contrairement au message `already exists` d'aujourd'hui qui ne part que sur stderr). Dans les deux modes, une surcouche de projet remplace un fichier du pack au même chemin, en ajoute un nouveau à un chemin absent du pack (Question H), et `project.yaml` seul est fusionné clé par clé : le pack fournit ce qu'il déclare, le projet garde ses propres clés (ex. `policy.free_agents`, une liste complétée des deux côtés, pas écrasée), aucun des deux n'écrase l'autre.
6. En mode copie, après un clone frais du projet (pas de `link-manifest.yaml`, non versionné), `pack update` refuse explicitement (« origine du pack inconnue ») plutôt que de deviner ou de recopier au hasard.
7. Une sortie compilée que l'ancienne version/épingle produisait et que la nouvelle ne produit plus est retirée (réutilise le mécanisme existant d'`unlink`/du link-manifest : suppression seulement si l'empreinte correspond encore à ce que `link` avait écrit).
8. `.armadai/state/` n'est jamais touché par une mise à jour de pack, quel que soit le mode ; `armadai validate` accepte chaque projet après la mise à jour (y compris un `{{var.name}}` encore non résolu dans ses fichiers `.armadai/`, puisque la résolution n'a lieu qu'au `link`) ; une mise à jour qui rendrait un projet invalide ne modifie aucune de ses sorties compilées (même garde qu'`init --pack` aujourd'hui).
9. Une surcouche propre à un projet ne modifie jamais le pack en cache : deux projets référençant le même pack, une surcouche ajoutée dans l'un seulement — le cache de la source (fichiers et empreintes) est identique octet pour octet avant et après cette surcouche, et l'autre projet, relié (`link`) sans rien changer de son côté, compile des sorties strictement identiques à ce qu'il compilait avant que le premier projet ajoute sa surcouche.
10. Le registre des projets référents gagne une entrée (pack, chemin) à chaque installation en mode référence ; `pack status`/`pack update` listent les projets référents d'un pack déplacé ou supprimé en le signalant par son chemin, sans jamais retirer son entrée du registre tout seuls.

**Sync forcé (objectif 2)**
11. Une commande de rafraîchissement forcé d'une source distante (git ou archive) met à jour le cache local même quand un pack du même nom s'y trouvait déjà, vérifié par un essai avec un faux registre local dont le contenu change entre deux appels.

**Scaffolding (objectif 4)**
12. `pack new --empty <nom>` crée un pack natif minimal (`pack.yaml` `format: 1`, arborescence du format canonique) qu'`armadai validate <dossier>` accepte sans erreur.
13. `pack new --from-project <nom>` copie le `.armadai/` courant (hors `link-manifest.yaml`, `state/`) en un pack natif qui passe la même validation.
14. `pack new <nom>` sans drapeau mène un assistant interactif qui produit le même résultat que `--empty` au minimum (nom, description), vérifiable en mode non interactif équivalent (règle T9 de l'étape 3, déjà en vigueur pour `new agent`/`new flow`).

**Variables (objectif 3)**
15. Un `{{var.name}}` dans un bloc `native:` de `project.yaml` (ex. un chemin de `native.claude.permissions.additionalDirectories`) ou dans le corps d'un agent, d'une skill ou d'une commande du pack n'est jamais résolu dans `.armadai/` lui-même (`init`/`pack update` l'y laissent littéral) ; seule la sortie compilée par `link` (`.claude/settings.json`, les fichiers d'agents/skills/commandes écrits) porte la valeur résolue, choisie par priorité croissante entre les trois couches (fichier versionné, puis fichier local non versionné, puis `ARMADAI_VAR_<NOM>`) : l'environnement l'emporte sur le fichier local, qui l'emporte sur le fichier versionné du projet.
16. Un `{{var.name}}` absent des trois couches produit, dans la sortie compilée, un avertissement nommé et une valeur vide — jamais un blocage silencieux, jamais le repère littéral envoyé à l'assistant.

**Signal de nouvelle version (objectif 5)**
17. `pack status` (et les trois reprises : `pack sync`, `list`/`inspect`, `link`) signalent un pack dont le cache et l'index déjà synchronisés contiennent une version différente du verrou ou des fichiers qu'un projet référence ou a installés, sans qu'aucun appel réseau n'ait lieu pendant l'exécution de ces commandes (vérifié en observant qu'aucune commande de socket/réseau n'est atteinte, reprise de la garantie déjà testée pour `link`).

**Décidés pendant l'exécution**
18. Le gate de délégation refuse une délégation hors topologie quand la vue effective d'un projet référençant un pack ne peut pas s'ouvrir (verrou ou instantané manquant, par exemple) ; un projet invalide pour une raison sans rapport avec un pack reste sans avis, comme pour un projet invalide ordinaire aujourd'hui.
19. `pack update <version>` avec une version hors de la plage déclarée dans `project.yaml` refuse explicitement, en nommant la plage et la version demandée, sans rien changer au verrou ni aux sorties compilées.
20. `pack add`/`pack update` sur un projet déjà invalide avant leur exécution refusent avec un message qui ne blâme pas le pack (« the project is already invalid… ») ; seule une mise à jour qui introduit elle-même une nouvelle erreur produit le message « would make the project invalid » (M13) — les deux cas sont distingués chacun par son propre test.
21. Une URL de source de pack affichée (`pack status`, un message d'erreur, `pack sync`) masque seulement ce qui est un secret (`user:pass@`, une requête, un utilisateur sur http/https) ; une URL SSH (`git@hôte:chemin`) s'affiche telle quelle, sans masquage.
22. Si `link` échoue après que `pack add`/`pack update` ont écrit de nouveaux fichiers, tout est remis dans l'état d'avant — `.armadai/` (`project.yaml`, verrou) et les sorties compilées (`.claude/`, `opencode.json`) — dans les deux modes ; la restauration ne copie ni ne supprime que les chemins que `link` a effectivement touchés, jamais des arbres entiers (mesuré : une mémoire bornée sur un worktree de taille réelle, pas la régression à 1,28 Go de RSS).
23. Une fusion de `project.yaml` en mode copie qui change sa forme écrite (commentaires, mise en page perdus) émet un avertissement nommé, jamais silencieuse.
24. `pack update` en mode copie distingue par un message propre l'absence de toute trace d'un pack installé (M9) d'une trace illisible ou absente après un clone (M8) ; un projet qui porterait deux origines de copie à la fois refuse plutôt que de choisir au hasard laquelle mettre à jour.
25. Deux écritures concurrentes dans le registre des projets référents (deux `pack add`/`pack update` en parallèle) ne perdent aucune des deux entrées (verrou de fichier) ; un registre d'un format non supporté refuse avec une erreur nommée, sans rien écraser.
26. `armadai skills list`/`skills show` lisent la vue effective d'un projet référençant un pack, comme `list`/`inspect` ; `inspect` et `skills show` indiquent, pour un élément venant du pack, sa couche d'origine (forme validée : `Source: pack <nom>, <chemin>`, et pour un agent-instance `, from: <template> (pack <nom>, <chemin>)`).
27. Un tag supprimé dans la source d'un pack référencé produit un avertissement nommé (`pack sync`) sans modifier le verrou, qui garde le commit qu'il avait déjà ; le cas où la source a aussi perdu ce commit (après un `git gc`) est un défaut connu, hors de ce lot, suivi par une issue séparée — pas un critère vérifiable ici.
28. Un pack créé par `pack new --empty` ou `--from-project` porte un `.gitkeep` dans chacun de ses dossiers vides ; l'installation de ce pack (`init --pack`) ne le signale jamais comme un fichier ignoré du pack.
29. `armadai pack --help` affiche une description longue validée par Dimitri, et le test qui vérifie qu'une commande conservée a toujours une description d'aide couvre `pack`.

## 6. Risques

| # | Risque | Parade |
|---|---|---|
| R1 | Le périmètre couvre 5 capacités disjointes dans un seul lot, avec 29 critères d'acceptation (17 de la spec initiale, 12 ajoutés pendant l'exécution) : au-delà d'une dizaine, la skill `briefing` recommande de couper. Dimitri a tranché « un seul lot, tout » (2026-11-03) malgré ce risque, en connaissance de l'ampleur prise par le cadrage du mode référence puis par les décisions prises en route. | Le plan a découpé les cinq capacités en 18 tâches indépendantes autant que possible ; la revue (`reviewer`) et la validation portent sur l'ensemble, tâche par tâche (`guardian`) puis globalement. |
| R2 | Ajouter une traçabilité d'origine de pack dans le link-manifest change un format que la règle du dépôt protège (v1, champs optionnels seulement). | Un champ optionnel nouveau (la section `packs:` comprise), jamais un changement de version ; un test lit un manifeste de la version précédente (règle déjà en vigueur, à appliquer ici aussi). |
| R3 | Le bloc `native:` est un passe-plat JSON libre : une substitution récursive dedans peut toucher une valeur qui n'est pas un chemin (un entier, un booléen envoyé tel quel à Claude Code/OpenCode) et la corrompre si la substitution est appliquée sans discernement. | Ne substituer que dans les valeurs `String` du JSON, jamais convertir un type ; test par mutation sur un bloc `native` mêlant chemins et valeurs non textuelles. |
| R4 | Trois couches de résolution de variables (environnement, fichier local, fichier versionné) multiplient les cas de priorité et de recouvrement partiel (une variable dans le fichier versionné, une autre seulement en local) à bien tester. | Une matrice de tests par couche présente/absente, mutée (règle du dépôt : une mutation par test). |
| R5 | Un verrou qui n'avance pas correctement (bug dans `pack update`) ferait dépendre un projet du contenu volatile du cache au moment du `link`, recréant silencieusement le risque que l'épinglage (Question G) devait justement fermer. | Un test qui fige le cache entre deux `link` sans `pack update` : les sorties ne doivent pas varier tant que le verrou n'a pas avancé. |
| R6 | La fusion clé par clé de `project.yaml` (Question H) doit traiter correctement une clé-liste que les deux côtés complètent (ex. `policy.free_agents`), pas seulement un remplacement scalaire : une fusion naïve écraserait une liste au lieu de la compléter. | Tests par mutation sur une fusion à listes des deux côtés, en plus du cas scalaire simple. |
| R7 | Le registre des projets référents peut devenir inexact (projet déplacé ou supprimé, chemin devenu invalide) : une entrée stale listée comme si elle existait encore induit en erreur. | Décidé (Question L) : un chemin invalide est signalé, jamais retiré en silence (cohérent avec l'anti-objectif « jamais une perte non signalée ») ; test avec un chemin de projet supprimé entre l'installation et un `pack status`. |
| R8 | Résoudre une plage semver suppose une liste de versions : l'index la donne s'il en liste, des tags git `<pack>-vX.Y.Z` sinon ; une source archive n'a ni l'un ni l'autre par défaut (pas de tags) et devient inutilisable pour une plage sans index. | Décidé : l'index est obligatoire pour une source archive dès qu'une plage est utilisée (documenté) ; un repli par sous-modules Git reste à évaluer au plan si l'un ou l'autre mécanisme s'avère trop complexe en pratique. |
| R9 | Garder `semver` hors d'`armadai-model` (portabilité pure du modèle, `cargo build -p armadai-model`) impose que toute résolution de plage passe par le binaire avant d'atteindre les fonctions pures ; une tentation de résoudre une plage « en passant » dans le modèle romprait cette garde déjà testée. | La fonction pure du modèle ne reçoit jamais une plage, seulement une version/commit déjà résolus ; `cargo build -p armadai-model` reste la barrière qui détecte une dépendance `semver` qui s'y serait glissée. |
| R10 | Une restauration naïve après un `link` en échec (copier/supprimer des arbres entiers de `.claude/`) coûte une mémoire proportionnelle au worktree entier : mesuré à 1,28 Go de RSS avant correction. | Décidé : la restauration ne touche que les chemins que `link` a effectivement écrits ou retirés, jamais une copie d'arbre entier (critère 22) ; mesuré après correction (RSS bornée). |
| R11 | Le registre des projets référents, écrit par plusieurs commandes `pack add`/`pack update` en parallèle (plusieurs projets mis à jour en même temps sur une machine), peut perdre une entrée en écriture concurrente : mesuré dans 27 essais sur 160 avant un verrou de fichier. | Décidé : un verrou de fichier protège chaque écriture (critère 25) ; la mesure de régression, répétée, n'a plus montré de perte. |

## Décisions de commandes, noms et formats (closes au plan, section 7)

Le nommage que la spec initiale renvoyait « à trancher au plan » est désormais fixé (validé par Dimitri, section 7 du plan) :
- Commandes : `armadai pack add <name>[@<range>] [--source <url>]`, `pack sync [--source <url>]`, `pack status`, `pack update [<version>]`, `pack new <name> [--empty | --from-project] [--description …] [--dir …]` ; `init --pack` reste le mode copie. Plage par défaut de `pack add` sans `@` : `^<version résolue>`.
- Fichiers : clé `pack: { name, source, version }` dans `project.yaml` ; verrou `.armadai/pack.lock` ; variables `.armadai/vars.yaml` (versionné) et `.armadai/vars.local.yaml` (non versionné) ; index de source `armadai-packs.yaml` ; registre `~/.config/armadai/pack-referents.yaml` ; versions synchronisées `~/.config/armadai/registry/packs/<clé>/versions.yaml` ; tags `<pack>-vX.Y.Z`.
- Repli par sous-modules Git (évalué, **non retenu**) : ajouterait une deuxième source de version contredisant la première, ne serait pas cloné par le mécanisme actuel sans changement, et chaque sous-module privé demanderait ses propres identifiants qu'une source archive ne peut pas porter. La résolution par index + tags préfixés tient en une fonction pure, elle n'est pas « trop complexe » au sens de la décision de Dimitri.
- Portée de la substitution (Question Q5 du plan) : dans `project.yaml`, les seules valeurs texte du bloc `native` ; les corps (après le frontmatter) des agents, templates, commandes et `SKILL.md`. Rien dans les frontmatters, `scripts/`/`references/` d'une skill, ni `native/<cible>/` : jamais touché, donc jamais cassé.
- Forme de l'index de source (Question Q6 du plan) : la version du contenu au commit courant, plus l'historique par les tags `<pack>-vX.Y.Z`.

## Défauts mesurés pendant l'exécution, hors lot (issues à ouvrir après le lot)

Mesurés pendant les tâches, confirmés avec Dimitri comme hors périmètre de ce lot, à suivre par des issues séparées plutôt que par un critère de cette spec :
1. Un tag supprimé puis un `git gc` de la source rend un verrou irréparable (le commit n'est plus récupérable) — `pack sync` ne peut qu'avertir, pas réparer.
2. Préexistant (hors de ce lot) : `link` suit un lien symbolique d'agent qui pointe hors du projet et recopie son contenu dans `.claude/agents`.
3. `git pull --ff-only` d'une source dont l'historique a été réécrit par son origine échoue définitivement (pas de remède automatique prévu).
4. `crates/armadai/src/skills_registry/sync.rs` clone sans séparateur `--` avant l'URL (même classe d'injection que celle fermée en tâche 4-5 de ce lot pour `starters_registry`).
5. Un jeton dans le `#fragment` d'une URL de `registries.yaml` reste affiché en clair dans un avertissement de synchronisation (`armadai-core`, préexistant).

## Questions ouvertes

- Le moment où `armadai-packs` est poussé (« une fois un pack paramétré », mot de Dimitri) n'est pas une question de conception de ce lot : à rappeler à Dimitri une fois qu'un pack réel portera le paramétrage.
